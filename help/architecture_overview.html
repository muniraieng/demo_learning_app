1. Yeh Architecture Kya Hai?

Yeh app CLEAN Architecture + MVVM pattern use karta hai. Har layer ka apna kaam hai, aur layers ek doosre se independent hain. Dependency rule: outer layer inner layer ko call karti hai, inner layer ko outer ka pata nahi.

3. Har Layer Ka Role

Presentation Layer
  • Screens: UI dikhate hain, koi business logic nahi
  • ViewModels: State manage karte hain (GetX ya Riverpod)
  • Widgets: Reusable UI components (CourseCard)
Domain Layer
  • Entities: Pure Dart classes (Course, Lesson) — koi framework dependency nahi
  • Repository Interfaces: Abstract classes — define karti hain kya karna hai, kaise nahi
  • UseCases: Ek ek kaam karte hain (Single Responsibility)
Data Layer
  • Repository Implementations: Domain interfaces ko implement karte hain
  • DataSources: Remote (JSON asset) aur Local (Drift DB)
  • Models: JSON serialization/deserialization
Core Layer
  • Constants: App-wide constants
  • Errors: Failure classes (ServerFailure, AuthFailure, etc.)
  • Network: Dio client + NetworkInfo
  • Storage: SecureTokenStorage (flutter_secure_storage)
  • Utils: InputValidators

4. MVVM Pattern — Har Screen Mein

Login Screen (GetX)
Model: AuthRepositoryImpl (data layer) ViewModel: LoginViewModel extends GetxController - email, password, isLoading, error (all .obs) - login() method View: LoginScreen extends GetView - TextFormField, FilledButton - Obx() se reactive UI
Dashboard Screen (GetX)
Model: CourseRepositoryImpl (data layer) ViewModel: CourseDashboardViewModel extends GetxController - state, courses, failure (all .obs) - load() / refresh() methods View: CourseDashboardScreen extends GetView - ListView, CourseCard, RefreshIndicator - Obx() se reactive UI
Detail Screen (Riverpod)
Model: CourseRepositoryImpl (data layer) ViewModel: CourseDetailViewModel extends AutoDisposeFamilyNotifier - build(courseId) → initial state - load() / completeLesson() methods View: CourseDetailScreen extends ConsumerWidget - ref.watch(provider) se reactive UI - ref.read(provider.notifier) se actions

5. Data Flow — Ek Request Ka Safar

1. User taps "Continue" on CourseCard │ ▼ 2. Get.to(() => CourseDetailScreen(courseId: c.id)) │ ▼ 3. CourseDetailScreen build() call │ ref.watch(courseDetailViewModelProvider(courseId)) │ ▼ 4. CourseDetailViewModel.build(courseId) │ Future.microtask(() => load()) │ ▼ 5. load() → GetCourseDetailUseCase.call(courseId) │ ▼ 6. CourseRepositoryImpl.getCourseDetail(courseId) │ _safeCache() → Drift DB se read │ ▼ 7. CourseLocalDataSource.getCachedCourses() │ ▼ 8. AppDatabase.getCachedCourses() │ SELECT * FROM courses │ ▼ 9. Result → Repository → UseCase → ViewModel │ ▼ 10. state = CourseDetailState(course: course) │ ▼ 11. UI rebuild → Lessons list dikhti hai

6. State Management — GetX vs Riverpod

┌─────────────────────────────────────────────────────────────┐ │ GetX (Login + Dashboard) │ │ │ │ Controller: extends GetxController │ │ State: .obs variables (reactive) │ │ UI: Obx(() => ...) widget │ │ DI: Get.put() / Get.find() │ │ Nav: Get.to() / Get.offAll() │ │ │ │ Pros: Simple, fast, less boilerplate │ │ Cons: Less type-safe, global state │ └─────────────────────────────────────────────────────────────┘ ┌─────────────────────────────────────────────────────────────┐ │ Riverpod (Detail Screen) │ │ │ │ Notifier: extends AutoDisposeFamilyNotifier │ │ State: Immutable State class │ │ UI: ref.watch(provider) / ref.read(provider) │ │ DI: Provider graph (compile-time safe) │ │ Cleanup: autoDispose (auto memory cleanup) │ │ │ │ Pros: Type-safe, testable, no context needed │ │ Cons: More boilerplate │ └─────────────────────────────────────────────────────────────┘
